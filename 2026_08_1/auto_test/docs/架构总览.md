# NR/LTE 基站自动化测试框架 — 架构总览

> 面向：潜在采购方 / 新接手工程师 / 技术评审
> 一句话定位：**面向 NR/LTE 基站设备的端到端自动化产测框架**——一键完成「起基站 → 配置仪器 → 扫频段/功率 → 采集测量 → 出 Excel 报告」，把原本几小时的人工手动测试压缩成无人值守的自动流程。

---

## 1. 它解决什么问题

传统基站射频/协议测试要工程师手动操作仪器（R&S CMW500 类综测仪）、逐个频段/带宽/功率点配置、肉眼抄读 BLER/功率、再手工拼 Excel。**慢、易错、不可复现**。

本框架把整条链路自动化：

- **自动编排**：远程起停基站（gNB/eNB）、配置仪器、切换频段/信道
- **自动测量**：BLER、发射功率、TXP 等关键指标，带自动重试与就绪判定
- **自动出报告**：结构化 JSON + 格式化 Excel（含柱状图、多脚本汇总、横向对比、失败标红）
- **完整留痕**：仪器 SCPI 流量、基站运行日志、信令截图、核心网日志全程归档，按用例（case）分段

## 3. 数据流（一次测试的生命周期）

```
配置(souren_config)         →  main.py 载入待测脚本列表
  │
  ▼
SourenManager.initialize    →  连接仪器、准备执行目录 log/execution_<时间戳>/<用例>/
  │
  ▼
PythonScriptExecutor.run    →  执行测试脚本：
  │    case_start()            远程起基站(NSA/SA) + 起日志抓取 + 线损表/RF 配置
  │    case_body()             扫频段×range×带宽：切信道→等 UE 连接→测 BLER/TXP
  │    case_clear()            停测量、关小区、停基站、重启网页
  │
  ▼  (每条 ap.send/query)
  仪器 SCPI 收发 + 数据提取(extract_index) + 就绪/重试判定(AST 预期值)
  │
  ▼
SourenResultSaver           →  *_results_*.json（原始执行数据 + 提取数据点）
  │
  ▼
ResultExporter              →  *_results_*.xlsx（执行汇总 / 详细记录 / 数据分析图表）
  │                            summary_charts_*.xlsx（多脚本横向对比 / 最终数据汇总）
  ▼
远程日志回传                →  基站日志、SCPI/信令日志、PVT/LTE 截图、核心网日志
                              服务器持久日志 /tmp/ubuntu_server.log（按 case 分段）
```

## 4. 技术亮点（这套系统「值钱」的地方）

以下是通用测试框架里少见、且踩过坑才做得对的关键设计：

1. **pty 伪终端抓完整基站日志**
   NR/LTE 程序会检测是否运行在真实终端（tty），非 tty 时会大幅削减输出（丢掉 MT_PS/NR_MAC/NR_RRC/PHY 等关键模块日志）。框架用 `pty.openpty()` 伪造终端，确保抓到完整调试日志、ANSI 码、全部模块输出。**这是保证日志完整性的核心，普通 subprocess PIPE 做不到。**

2. **AST 解析自动识别 query 预期值 + 智能重试合并**
   执行器用 AST 分析测试脚本里 `ap.query()` 后紧跟的 `if result == expected` 条件，自动提取预期值。当结果不匹配时，把多次重试**合并成一条 "Check" 记录**，而不是刷屏记录每次尝试，报告更干净、可读。

3. **精确的进程生命周期与日志防截断**
   通过「包装脚本 + `oom_score_adj=-1000` 看守进程 + 会话级 pkill」精准感知孙进程（nr-softmodem）死亡瞬间，保证进程真正退出前的最后日志不被截断；并在退出瞬间自动收集 OOM/内存诊断。

4. **按 case 分段的全链路留痕**
   仪器 SCPI 流量（客户端侧记录，兼容新版仪器网页不再推送 SCPI 的情况）、基站运行日志、信令/截图、核心网日志，全部按用例归档；服务器持久日志用 banner 分段并回传客户端 `souren_execution.log`，两侧信息一致、可事后复盘。

5. **失败可视化**
   测量在异常条件（UE 未连接、BLER 未就绪）下读到的 0.000 会被标记为失败，图表中以**红色柱 + 红字**与真实测得值区分，避免"失败读数被当成正常数据"。

6. **面向硬件的鲁棒性**
   仪器断连自动重连/重建资源管理器；远程服务不可达时优雅降级（no-op 而非崩溃）；大文件 gzip 压缩回传。

## 5. 关键能力清单

## 6. 部署与运行

**环境依赖**
- Windows 测试主机：Python 3 + `pyvisa` / `pyvisa-py` / `pandas` / `openpyxl` / `flask`
- Ubuntu 主机：Python 3 + Selenium + Firefox/geckodriver；基站软件与综测仪 Web 服务

**Ubuntu 服务端（必须常驻）**
```bash
# 从 Windows 上传
scp auto_test/control_ubuntu/ubuntu_server.py yc@<UBUNTU_IP>:~/ubuntu_server.py
# Ubuntu 上重启
sudo pkill -f ubuntu_server.py
cd ~ && python3 ubuntu_server.py &
netstat -tuln | grep 9999   # 确认监听
```

**客户端运行**
```bash
python auto_test/main.py --run             # 执行全部配置脚本
python auto_test/main.py --list            # 列出待测脚本
python auto_test/main.py --py-file yc1100/test_fixed_power.py   # 指定脚本

cd auto_test/web_dashboard && python app.py # 看板 http://localhost:5000
```

**配置入口**：`souren_config.py`（待测脚本列表、仪器 IP、循环次数、用例目录映射）

## 8. 已知边界（诚实披露）

- 当前强绑定特定硬件：CMW500 类综测仪 + 指定 Ubuntu 基站发行版（版本号硬编码），换环境需适配。
- 部分连接参数（IP、路径、凭据）散落于配置与服务端，`ubuntu_server.py` 另存一份 VERSION，需人工保持同步。
- 无自动化测试 / CI；用户可见文案与注释以中文为主。

> 这些边界正是"产品化"的改造方向：配置集中化、硬件抽象层、基础测试与 CI。做完可显著提升可交付性与外部价值。
